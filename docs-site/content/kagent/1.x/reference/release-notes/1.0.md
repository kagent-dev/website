## 1.0.0

kagent 1.0 runs every agent on [Agent Substrate](https://github.com/agent-substrate/substrate), an open source runtime built for AI agents. Agent Substrate runs each conversation in its own sandbox, suspends it when idle, and resumes it on demand. Because of that foundation, 1.0 changes how an agent runs, how you declare one, and which custom resources exist. For how the pieces fit together, see the [kagent architecture]({{< link path="about/architecture/kagent" >}}) and [Agent Substrate architecture]({{< link path="about/architecture/agent-substrate" >}}) pages.

> [!IMPORTANT]
> No upgrade path exists from 0.10.x to 1.0. Moving an existing installation is a migration to a new installation with a new database, and Session history does not carry over. For the options and their trade-offs, see [Upgrade paths](#upgrade-paths).

For the component versions that this release pins and the Kubernetes version that it is tested against, see [Version support]({{< link path="reference/versions#what-a-kagent-release-includes" >}}).

### How agents run

1.0 moves the runtime off Kubernetes Deployments. The move changes the cost of an idle agent and the isolation boundary around a running agent.

- **Each {{< gloss "Session" >}}Session{{< /gloss >}} runs as an {{< gloss "Actor" >}}Actor{{< /gloss >}} on {{< gloss "Agent Substrate" >}}Agent Substrate{{< /gloss >}}**, rather than as a long-lived Deployment that serves every Session for one agent.
- **Sessions suspend between turns.** When a turn ends, Agent Substrate writes the Actor's memory and filesystem to a {{< gloss "Snapshot" >}}snapshot{{< /gloss >}} and releases the {{< gloss "Worker" >}}Worker{{< /gloss >}} that hosted it. The next message restores that snapshot onto whichever Worker is free. For the lifecycle, see [Suspend and resume]({{< link path="about/substrate-runtime/suspend-and-resume#suspension-between-turns" >}}).
- **Every agent runs in a gVisor sandbox by default.** 0.10.x relied on a Kubernetes `securityContext` to constrain an agent. 1.0 provides process, network, and filesystem isolation without per-agent security context configuration. For what the sandbox separates, see [Sandboxing]({{< link path="about/substrate-runtime/sandboxing#what-the-sandbox-separates" >}}).

### How you declare an agent

The single 0.10.x Agent resource described both what an agent does and how it runs. 1.0 separates those concerns across two reusable resources, pairs them in a third, and tracks each running Session as a fourth object.

- **A {{< gloss "Harness" >}}Harness{{< /gloss >}} defines how an agent is allowed to run**, including its runtime, workload image, {{< gloss "WorkerPool" >}}WorkerPool{{< /gloss >}}, and snapshot storage. One Harness serves many agents, so expect fewer Harnesses than you had 0.10.x Agents.
- **An {{< gloss "AgentTemplate" >}}AgentTemplate{{< /gloss >}} defines what an agent does**, including its model, system prompt, tools, skills, and plugins.
- **An {{< gloss "Agent" >}}Agent{{< /gloss >}} pairs one AgentTemplate with one Harness.** `spec.template` takes either a reference to an existing AgentTemplate or a complete inline spec. `spec.harnessRef` takes only a reference. The Agent reports readiness. Callers address the Agent, not the AgentTemplate or the Harness.
- **A Session is one running conversation** with an Agent. Unlike a Harness, an AgentTemplate, or an Agent, a Session is not a custom resource. kagent's gRPC API creates each Session, and kagent's database stores it.

A Harness and an AgentTemplate do not reference each other. Neither resource has a field that names the other, so only an Agent connects them. For the full model, see [Core concepts]({{< link path="about/core-concepts#agent" >}}).

The custom resource definition (CRD) API group also moves from `kagent.dev/v1alpha2` to `api.kagent.dev/v1alpha3`. kagent does not convert resources between the two groups. 1.0 no longer bundles kmcp, so it does not install the `mcpservers.kagent.dev` CRD. 1.0 also no longer bundles the Grafana Model Context Protocol (MCP) server, so it does not create the `kagent-grafana-mcp` RemoteMCPServer. 0.10.x and 1.0 cannot run side by side on one cluster, because both charts name their ClusterRoles after the release. To keep 0.10.x serving while you move, install 1.0 on a second cluster.

### New capabilities

The following features are new in 1.0 and have no 0.10.x counterpart.

- **Multi-harness support:** Besides the built-in `kagent` harness, a Harness can run Codex, Claude, or a container image of your own that implements kagent's Agent2Agent (A2A) contract. For what each harness supports, see [Choose a harness]({{< link path="agents/agent-harness#choose-a-harness" >}}).
- **Actors on Micro-VMs:** gVisor remains the default sandbox class. The `microvm` class places a hypervisor boundary between the workload and the host. For how a pool selects its class, see [Sandbox classes]({{< link path="about/substrate-runtime/sandboxing#sandbox-classes" >}}).
- **Access to destinations with EgressPolicy resources:** You can apply an EgressPolicy to an Agent or a SandboxTemplate to inject a credential into requests that the Agent or SandboxTemplate sends to a destination. For the procedure, see [Grant access to a destination]({{< link path="agents/egress-policies#grant-access-to-a-destination" >}}).
- **Standalone sandboxes with SandboxTemplates:** A SandboxTemplate defines a scratch environment that is independent of any Session. A person, or an agent through the kagent MCP server, creates a Sandbox from the template to run commands and transfer files. For the procedure, see [Create a SandboxTemplate]({{< link path="about/substrate-runtime/standalone-sandboxes#create-a-sandboxtemplate" >}}).
- **Actor identity for model authentication:** A ModelConfig can authenticate to a model endpoint as the calling Actor instead of with a stored credential. When you set `actorJwt`, the egress gateway sends a token that identifies the Actor to a model endpoint that you run, so the ModelConfig does not need a Secret. For the fields, see [Authenticate as the Actor]({{< link path="setup/model-providers/about-model-providers#authenticate-as-the-actor" >}}).
- **Context compaction:** The `kagent` harness summarizes older Session events according to the `spec.kagent.compaction` block on the Harness. For the settings, see [Configure compaction]({{< link path="agents/context-management#configure-compaction" >}}).
- **Structured output:** You can constrain an agent's final answer to a JSON Schema, so that callers receive a response in a predictable shape. The AgentTemplate sets the schema in its `outputSchema` field or reads it from a ConfigMap. For an example, see [Set the schema inline]({{< link path="agents/structured-output#set-the-schema-inline" >}}).
- **Session sharing with share tokens:** A share token gives another account read-only access to one Session. For the access model, see [Share a Session]({{< link path="agents/share-a-session#a-share-is-a-capability-not-a-grant-to-a-user" >}}).
- **Scheduled runs:** You can run an Agent on a cron expression. Each execution sends a fixed prompt to a new Session, so scheduled runs do not continue an earlier conversation. For the procedure, see [Create a schedule in the UI]({{< link path="agents/scheduled-runs#create-a-schedule-in-the-ui" >}}).

### Removed and replaced resources

Each 0.10.x resource kind is replaced, removed, or carried forward in 1.0. The distinction matters when you plan a move. A replaced kind has a destination for its configuration. A removed kind does not.

| 0.10.x resource | Status in 1.0 |
| --------------- | ------------- |
| Agent | Replaced by an AgentTemplate, a Harness, and a new Agent in the `api.kagent.dev` group that pairs them. The two Agent kinds share a name and nothing else. |
| ToolServer | Replaced by {{< gloss "RemoteMCPServer" >}}RemoteMCPServer{{< /gloss >}}, which 0.10.x already served alongside it. |
| Memory | Replaced by `Harness.spec.kagent.memory`, so memory is a property of the runtime rather than of one agent. |
| SandboxAgent | Removed with no replacement. Every 1.0 agent runs in a sandbox by default. |
| MCPServer | Removed, because 1.0 no longer bundles kmcp or its controller. Run the MCP server outside of kagent, and set its URL on a RemoteMCPServer. The `kagent mcp` commands are removed with it. |
| AgentHarness | Removed, with no equivalent. It provisioned OpenClaw and Hermes coding-agent sandboxes with Slack and Telegram channels. |
| ModelConfig, ModelProviderConfig, RemoteMCPServer | Carried forward. `v1alpha3` keeps every field that `v1alpha2` defines except one, so an exported resource needs a new `apiVersion` and one field rename. The ModelConfig field `apiKeyPassthrough` is now `tokenPassthrough`, the same name that RemoteMCPServer uses for the same behavior. |

> [!IMPORTANT]
> The 1.0 Harness and the 0.10.x AgentHarness share part of a name and nothing else. AgentHarness provisioned coding-agent sandboxes, while Harness governs how any agent is allowed to run. Read Harness as a new resource rather than a renamed one.

Several Agent fields do not have a `v1alpha3` equivalent, including `a2aConfig`, `executeCodeBlocks`, `shareTools`, and `context`. A2A is always on in 1.0. A caller addresses an Agent at `/agents/{namespace}/{name}` over HTTP, or through the A2A `tenant` field over gRPC. Tool bindings also have a new shape. A 1.0 `ToolBinding` contains an `mcp` or `subAgent` block and does not have a `type` discriminator. For the field-by-field mapping, see [Agents become an AgentTemplate, a Harness, and an Agent]({{< link path="operations/upgrade-from-0x#agents-become-an-agenttemplate-a-harness-and-an-agent" >}}).

### Upgrade paths

Compatibility promises start at 1.0. Plan a migration from 0.10.x, not an upgrade.

- **0.10.x to 1.0 in place is not supported.** kagent does not migrate a 0.10.x database to 1.0. 1.0 requires a new PostgreSQL database.
- **Downgrade from 1.0 to 0.10.x is not supported.**
- **1.0 to a later minor release is supported.** From 1.0 onward, migrations are append-only and each minor release retains compatibility with the previous release line.

Moving an existing installation therefore means a migration. Install 1.0 on a second cluster, recreate your resources on it, and retire 0.10.x once the new installation answers correctly. Installing on the same cluster requires uninstalling 0.10.x first, so your agents are unavailable until 1.0 is running. Because 1.0 cannot read a 0.10.x database, Session history does not move to the new installation. For the full procedure, see [Upgrade from 0.x]({{< link path="operations/upgrade-from-0x#in-place-upgrade-blockers" >}}).
